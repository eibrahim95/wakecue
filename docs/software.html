Prayer times for years ahead

All five prayers are built. A rule picks its trigger with When::Prayer(prayer, minutes) or a fixed clock time, and you can have several rules at once. The lamp computes Fajr (19.5°), Dhuhr, Asr (standard shadow), Maghrib (sunset) and Isha (17.5°) itself, from the place in its stored block: the Egyptian General Authority of Survey method, and the same NOAA solar formulae the prototype's generated table came from. Nothing ten years wide sits in the image any more — the arithmetic runs on the boot that needs it, so the owner's place stands in for Cairo, and a test asks the new code for all 18,260 times of the old Cairo table. (Which clock the lamp reads those times against is still Egypt's, with its summer time; that part is the next step, and until then a place outside Egypt would get right astronomy read on the wrong clock.) A prayer time is in UTC, so it is unaffected by daylight saving or a law change. DST only matters for display and for rules you write in local time; that function is tested on 2026 and 2027 (this year it ends Thursday 29 October 2026 at 24:00 Egypt time). Maghrib is the moment the sun's upper edge reaches the horizon (−0.833°), not a fixed number of minutes after.

How often the lamp gives the minute on the published timetable. The reference is the Egyptian General Authority of Survey's own calendar, which Dar al-Ifta (fatwa 3012) says is the one to follow in Egypt: its published times for Mansoura on 152 days of January, March, June, September and November 2026, read from esa.gov.eg on 8 Nov 2026 and kept in core/tests/data/egas-mansoura-2026.csv. Each cell counts the days on which the lamp's minute is exactly the published one. The calculation was always the same; only the rounding changed. The Authority's table is the calculation rounded to the nearest minute, with no systematic offset on any prayer (the lamp's unrounded value minus the published minute averages within 0.2 minutes of zero for all five, and stays between about -0.5 and +0.6), and with the nearest-minute rule the lamp is never more than a minute from a published time (core/tests/egas_mansoura.rs pins this on all 760 times). The remaining differences are a minute here and there from the city's coordinates, which the Authority and the setup list do not give identically. Google's prayer card for Mansoura on 8 Nov 2026 shows exactly the Authority's numbers.

Other calculators. The Aladhan calculator (method 5) rounds to the nearest minute too and agrees with the lamp's unrounded values to within half a minute on Fajr, Dhuhr, Maghrib and Isha, but its Asr is on average half a minute later than both the lamp's and the Authority's, so that prayer can come out a minute apart from the Authority's table there. For Saudi Arabia, the same arithmetic with the Umm al-Qura method (Fajr 18.5°, Isha 90 minutes after Maghrib) agrees with Aladhan's Umm al-Qura method for Makkah and Riyadh the same way. Aladhan lengthens Isha to 120 minutes during Ramadan, and the lamp does not yet; the official Saudi calendar could not be read automatically, so that comparison is against Aladhan only.

Calculation methods. The convention behind the times differs by country, and applying one country's in another puts a prayer minutes out: Makkah on 8 Nov 2026 has Fajr at 5:04 with the Egyptian 19.5° and at 5:09 with Umm al-Qura's 18.5°, which is what Google shows there. The setup page now has a Calculation method box, filled with the suggestion for the place picked from the list and changeable. It offers 19 authorities (the Egyptian Survey Authority, Umm al-Qura, the Muslim World League, ISNA, Karachi, Diyanet in Turkey, Dubai, Kuwait, Qatar, Jordan, Morocco, Algeria, Tunisia, JAKIM, MUIS, Kemenag, France, Russia and the Gulf), taking their numbers from AlAdhan's published method list. Four of them also move prayers by fixed minutes, measured from AlAdhan's output over four dates in a year: Diyanet (Dhuhr +5, Asr +4, Maghrib +7), Dubai (Dhuhr +3, Maghrib +3), Morocco (Dhuhr +5, Maghrib +5) and Jordan (Maghrib +5). With each method's numbers the lamp's arithmetic agreed with AlAdhan's to within the rounding for every prayer I could compare, except the gaps below. The suggestion for a place is set only where its country has an authority of its own; every other place gets the Muslim World League as a default, and that is a default, not a claim about the country. Known gaps: Umm al-Qura's Isha is 120 minutes after Maghrib during Ramadan (the lamp has no Hijri calendar); no high-latitude rule is applied, so around 48° north and beyond in summer Fajr and Isha can be several minutes off an app's (Paris on 21 June: about 9); Iran's method sets Maghrib by a sun angle, which the lamp cannot follow, so Iranian places carry no suggestion.

The code

Rust all the way Every driver in the final build has a Rust path. The ring uses the C3's RMT peripheral (the esp-hal-smartled crate). The SSD1680 e-paper uses weact-studio-epd (vendored in firmware_ws/vendor/, so a refresh can be started and finished separately). The DS3231 and MP3 commands are already written and tested in core. The DS3231's second alarm can wake the chip every minute to redraw the clock. I haven't checked those crates' versions against esp-hal 1.2, so pin whichever versions compile together.

The Rust project is in the firmware_ws/ folder next to this page and has three parts: core (the five computed prayer times and the schedule over them, the lamp's own alarms, DST, clock registers, MP3 frames, the ramp curve, the stored settings, the menu, the button decoding and the INA219 reading: 65 unit tests and an 18,260-time check against the old Cairo table), settings-tool (reads and patches the settings block from the PC, the way back when the menu is stuck) and wakecue (the lamp itself on esp-hal: display, buttons, alarms, sleep). What is not written yet is the ring and the MP3 card. The schedule is a list of rules in the stored settings block, edited from the menu or with settings-tool; this is how core spells three of them (see What you can schedule):

rules, as core spells them
const RULES: [Rule; 3] = [
    // Ring ramps deep red → amber → warm white over 15 minutes, finishing exactly at Isha
    Rule { days: ALL_DAYS, when: When::Prayer(Prayer::Isha, 0), action: Action::Sunrise { ramp_min: 15 } },
    // Isha's own track (/mp3/0005.mp3), fading in over a minute
    Rule { days: ALL_DAYS, when: When::Prayer(Prayer::Isha, 0), action: Action::Play { track: 5, volume: 20, fade_in_s: 60 } },
    // Example: Sun–Thu at 07:30 Egypt time, track 6 (DST handled automatically)
    Rule { days: 0b0001_1111, when: When::Local(7 * 60 + 30), action: Action::Play { track: 6, volume: 15, fade_in_s: 60 } },
];
The wake-then-sleep cycle, in outline

A sketch of the shape, not the code: the real boot path is firmware_ws/wakecue/src/bin/main.rs, and it runs on the board (see the build log). The 1.2 release changed the sleep API: a pin you listen(Event::LowLevel) on is the wake source, and RtcioWakeupSource is gone. The touch pad on GPIO4 is the same shape but the opposite level: it is armed on a high, because the module in hand has no A/B pads to flip (see the build log).

outline
// 1) Read time and status from the DS3231 (UTC)
i2c.write_read(I2C_ADDR, &[ds3231::REG_TIME], &mut t)?;
let now_min = ds3231::parse_time_registers(t).div_euclid(60);

// 2) If the alarm woke us, run the event that just came due
if let Some(ev) = next_event(now_min - 2, &RULES, &prayers) {
    if ev.utc_min <= now_min { run(ev.action); }
}

// 3) Clear A1F, otherwise INT stays low and sleep is refused
i2c.write(I2C_ADDR, &[ds3231::REG_STATUS, status & !ds3231::STATUS_A1F])?;

// 4) Program the next event (date + hour + minute) and enable Alarm 1
let a = ds3231::alarm1_registers(next_event(now_min, &RULES, &prayers)?.utc_min);
i2c.write(I2C_ADDR, &[ds3231::REG_ALARM1, a[0], a[1], a[2], a[3]])?;
i2c.write(I2C_ADDR, &[ds3231::REG_CONTROL, ds3231::CONTROL_ALARM1_ONLY])?;

// 5) Pins wake on low level, then deep sleep
let mut int = Input::new(p.GPIO3, InputConfig::default().with_pull(Pull::Up));
int.apply_wakeup_config(&WakeupConfig::default().with_low_power_path(true))?;
int.listen(Event::LowLevel);
LowPower::new(p.LPWR).sleep_deep(RtcSleepConfig::deep());
